# 追番进度快捷操作 详细设计

## 1. 背景与范围

本设计对应 `V2.0` 开发计划中的“追番进度快捷操作”任务。

当前追番模块支持逐集点击切换已看状态，但在常见场景中操作成本较高：

- 想一次性把进度设置到“看到第 N 集”；
- 想快速标记全看完；
- 想一键清空进度重新开始。

本次设计新增三类快捷操作能力：`看到第 N 集`、`一键看完`、`重置进度`，并保持与现有状态自动推导逻辑一致。

---

## 2. 设计目标

1. 提供三类快捷操作接口，减少逐集点击成本。
2. 快捷操作后统一更新 `watched_eps`、`status`、`last_watch_at`。
3. 快捷操作不影响 `track_date` 语义（开始追番时间保持不变）。
4. 前端在进度弹窗中新增快捷操作区，位置在**集数网格下方**。
5. 前端使用下拉列表限制“看到第 N 集”的输入范围为 `1..eps`。

---

## 3. 业务规则

### 3.1 状态机（沿用）

- `watchedCount == 0` -> `status = 0`（想看）
- `0 < watchedCount < totalEpisodes` -> `status = 1`（在看）
- `watchedCount >= totalEpisodes` -> `status = 2`（已看完）

### 3.2 三种快捷操作语义

- `看到第 N 集`：覆盖设置为已看 `[1..N]`。
- `一键看完`：覆盖设置为已看 `[1..eps]`。
- `重置进度`：覆盖设置为已看 `[]`。

### 3.3 数据写入规则

每次快捷操作写库时：

- 更新 `watched_eps`（有序、去重、范围合法）；
- 更新 `status`（按状态机自动推导）；
- 更新 `last_watch_at = 当前时间`；
- **不更新** `track_date`。

---

## 4. 接口设计

统一前缀：`/api/anime/progress`

统一返回包装：`Result<T>`

### 4.1 看到第 N 集

- Method: `PUT`
- Path: `/api/anime/progress/seen-to`

请求体：

```json
{
  "animeId": 1001,
  "episode": 7
}
```

成功响应：

```json
{
  "code": 200,
  "message": "success",
  "data": null
}
```

失败响应示例：

```json
{
  "code": 500,
  "message": "番剧不存在",
  "data": null
}
```

### 4.2 一键看完

- Method: `PUT`
- Path: `/api/anime/progress/complete`

请求体：

```json
{
  "animeId": 1001
}
```

成功响应：

```json
{
  "code": 200,
  "message": "success",
  "data": null
}
```

### 4.3 重置进度

- Method: `PUT`
- Path: `/api/anime/progress/reset`

请求体：

```json
{
  "animeId": 1001
}
```

成功响应：

```json
{
  "code": 200,
  "message": "success",
  "data": null
}
```

## 5. 后端改造设计

### 5.1 Service 层

在 `AnimeService` 新增：

- `void seenToEpisode(Long animeId, Integer episode)`
- `void completeAnime(Long animeId)`
- `void resetProgress(Long animeId)`

### 5.2 Controller 层

在 `AnimeController` 新增三个 `PUT` 接口，分别对应 `seen-to`、`complete`、`reset`。

### 5.3 Impl 层

在 `AnimeServiceImpl` 中：

1. 统一查询 `AnimeSubject` 和 `AnimeProgress`；
2. 根据快捷操作构造目标 `watched_eps`；
3. 复用统一的“状态推导 + 更新时间 + 落库”逻辑。

建议增加私有方法：

- `applyProgress(animeId, watchedEpisodes)`：统一写库行为；
- `buildRangeEpisodes(n)`：生成 `[1..n]` 列表。

### 5.4 参数与异常处理

- `animeId` 不存在：返回业务错误。
- `episode < 1`：返回业务错误。
- `episode > eps`：后端兜底裁剪为 `eps`（即使前端已限制）。
- `eps <= 0`：`seen-to/complete` 返回业务错误；`reset` 允许执行。

---

## 6. 前端改造设计

### 6.1 交互位置

在 `AnimeView` 进度弹窗内，**集数网格下方**新增快捷操作区。

### 6.2 交互控件

- 一个下拉框：选项为 `1..currentAnime.subject.eps`；
- 三个按钮：
  - `看到第N集`
  - `一键看完`
  - `重置进度`

### 6.3 提示交互策略

- 三个快捷操作在**成功时不弹提示框**。
- 用户通过集数勾选结果与状态标签变化直接感知成功。
- 仅在失败时弹出错误提示（如“操作失败，请重试”），提示方式复用 `AppNoticeDialog`。

### 6.4 前端数据同步

快捷操作成功后应同步：

- `currentAnime.progress.watchedEps`
- `currentAnime.progress.status`

并刷新列表或同步当前项，保证卡片状态与弹窗状态一致。

---

## 7. 验收标准

### 7.1 行为验收

- “看到第 N 集”后，已看为 `1..N`，状态正确。
- “一键看完”后，已看为 `1..eps`，状态为已看完。
- “重置进度”后，已看为空，状态为想看。

### 7.2 数据验收

- 每次快捷操作均更新 `last_watch_at`。
- 每次快捷操作均不修改 `track_date`。
- `watched_eps` 始终为合法范围内的升序数组。

### 7.3 前端验收

- 快捷操作区位于集数网格下方。
- “看到第 N 集”使用下拉选择，不可输入超出 `eps` 的值。
- 三个快捷操作成功后不出现提示弹窗；失败时出现错误提示。

---

## 8. 风险与处理

- 风险：前后端都改 `watched_eps`，若本地状态未同步可能出现短暂 UI 偏差。
  - 处理：操作成功后统一以后端结果或一致规则更新本地状态。
- 风险：`eps` 异常（0 或空）导致“看完”语义不明确。
  - 处理：后端明确校验并返回业务错误。

---

## 9. 结论

本方案在保持“状态由进度自动推导”原则不变的前提下，引入三种高频快捷操作，显著降低用户操作成本，同时通过下拉限制与后端兜底保证数据正确性，为后续筛选、排序与统计能力提供稳定输入。
