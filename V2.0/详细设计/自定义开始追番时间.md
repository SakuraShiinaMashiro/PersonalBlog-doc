# 自定义开始追番时间 详细设计

## 1. 背景与范围

本设计对应 `V2.0` 开发计划中的“自定义开始追番时间”任务。

目标是让用户在导入番剧时可指定“开始追番时间”（`track_date`），并在后续可手动修改；同时在追番列表卡片中展示“开始追番时间”和“最近观看时间”。

本次设计覆盖：

- 导入时可选自定义 `trackDate`；
- 已导入番剧可更新 `trackDate`；
- 卡片展示 `trackDate` 与 `lastWatchAt`；
- 明确重复导入与进度快捷操作对时间字段的影响边界。

本次不覆盖：

- 多用户隔离与权限控制；
- 批量更新追番时间；
- 复杂时区策略（按当前系统时区展示）。

---

## 2. 现有情况（基线）

### 2.1 数据层现状

当前 `blog_anime_progress` 已具备以下字段：

- `track_date`：开始追番时间（`DATE NOT NULL`）；
- `last_watch_at`：最近观看时间（`DATETIME NULL`）；
- `status`、`watched_eps` 等进度字段已按 V2.0 语义落地。

说明：数据库结构已满足本需求，不需要新增列。

### 2.2 后端现状

已实现能力：

- 导入接口 `POST /api/anime/import` 已支持幂等返回（`CREATED` / `UPDATED`）；
- 首次导入会初始化 `AnimeProgress`，`trackDate` 当前固定写入 `LocalDate.now()`；
- 重复导入只更新元数据，不更新 `progress`；
- 进度快捷操作会更新 `lastWatchAt`，且不改 `trackDate`。

现存缺口：

- 导入接口暂不支持传入自定义 `trackDate`；
- 暂无独立“修改追番时间”接口。

### 2.3 前端现状

已实现能力：

- 追番列表按 `progress.trackDate` 倒序展示；
- 导入弹窗已具备搜索并点击“导入”流程；
- 进度操作（看到第N集/一键看完/重置）已可用。

现存缺口：

- 导入请求仅传 `bgmId`，不能传 `trackDate`；
- 导入弹窗中尚无“开始追番时间”选择控件；
- 卡片未展示“开始追番时间”“最近观看时间”；
- 暂无“修改追番时间”前端交互入口。

---

## 3. 设计目标

1. 用户在导入时可指定开始追番时间；不指定则默认导入当天。
2. 重复导入保持幂等语义：即使传入 `trackDate` 也忽略，不覆盖历史值。
3. 用户可在导入后单独修改开始追番时间。
4. 追番卡片补充展示：
   - 开始追番时间（`trackDate`）
   - 最近观看时间（`lastWatchAt`）

---

## 4. 核心业务规则

### 4.1 导入与时间写入规则

- `CREATED`（首次导入）：
  - 若请求包含合法 `trackDate`，写入该值；
  - 否则写入 `today`。
- `UPDATED`（重复导入）：
  - 忽略请求中的 `trackDate`；
  - 不修改 `progress.track_date`。

### 4.2 修改追番时间规则

- 仅允许通过独立接口修改 `track_date`；
- 更新 `track_date` 不影响：
  - `watched_eps`
  - `status`
  - `last_watch_at`

### 4.3 进度操作与时间字段边界

- `toggle / seen-to / complete / reset`：
  - 可更新 `last_watch_at`；
  - 不更新 `track_date`。

---

## 5. 交互设计

### 5.1 导入弹窗交互（已确认方案）

采用“先选时间，再导入”：

1. 用户在导入弹窗内选择“开始追番时间”（默认今天，可清空）；
2. 用户点击某条搜索结果的“导入”按钮；
3. 前端请求携带 `bgmId + trackDate?`；
4. 后端按 `CREATED/UPDATED` 规则处理。

不采用“点击导入后再弹二次时间确认”的原因：

- 操作链路更短，减少一次打断；
- 用户在提交前即可感知最终写入值；
- 与现有导入流程兼容，改造成本更低。

### 5.2 追番卡片展示

在卡片信息区新增两行：

- `开始追番：YYYY-MM-DD`（无值显示 `--`）；
- `最近观看：YYYY-MM-DD HH:mm`（无值显示 `--`）。

### 5.3 导入后修改入口

在进度管理弹窗中增加“开始追番时间”编辑区：

- 展示当前 `trackDate`；
- 用户选择新日期后点击保存；
- 保存成功后提示并刷新本地展示顺序。

---

## 6. 接口设计

统一返回 `Result<T>`。

### 6.1 导入接口增强

- Method: `POST`
- Path: `/api/anime/import`

请求体：

```json
{
  "bgmId": 123456,
  "trackDate": "2026-03-21"
}
```

字段说明：

- `bgmId`：必填，Bangumi 条目 ID；
- `trackDate`：可选，格式 `yyyy-MM-dd`。

响应示例（首次导入）：

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "action": "CREATED",
    "message": "导入成功"
  }
}
```

响应示例（重复导入）：

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "action": "UPDATED",
    "message": "已存在，已刷新番剧信息"
  }
}
```

### 6.2 修改追番时间接口（新增）

- Method: `PUT`
- Path: `/api/anime/track-date`

请求体：

```json
{
  "animeId": 1001,
  "trackDate": "2026-01-15"
}
```

成功响应：

```json
{
  "code": 200,
  "message": "success",
  "data": null
}
```

失败响应示例：

```json
{
  "code": 500,
  "message": "追番时间格式错误，请使用 yyyy-MM-dd",
  "data": null
}
```

## 7. 后端改造点

### 7.1 Controller

- `importAnime` 支持接收可选 `trackDate`；
- 新增 `updateTrackDate` 入口；
- 逐步替换 `Map<String, Object>` 为专用 DTO（推荐）。

### 7.2 Service

- `importFromBangumi` 增加可选 `trackDate` 参数；
- 新增 `updateTrackDate(Long animeId, LocalDate trackDate)`；
- 统一日期解析与校验逻辑，避免控制层重复处理。

### 7.3 校验规则

- `trackDate` 格式必须为 `yyyy-MM-dd`；
- `trackDate` 不能为空（在更新接口中）；
- 建议限制：`trackDate` 不得晚于当前日期。

---

## 8. 前端改造点

### 8.1 API 层

- `animeApi.import(data: { bgmId: number; trackDate?: string })`；
- 新增 `animeApi.updateTrackDate(animeId: number, trackDate: string)`。

### 8.2 视图层

- 导入弹窗新增日期选择器（默认今天）；
- 导入请求携带 `trackDate`（可选）；
- 卡片新增时间展示两行：开始追番、最近观看；
- 进度弹窗新增“修改开始追番时间”交互。

### 8.3 展示格式

- `trackDate`：`yyyy-MM-dd`；
- `lastWatchAt`：`yyyy-MM-dd HH:mm`；
- 空值统一展示 `--`。

---

## 9. 验收标准

1. 首次导入不传 `trackDate` 时，`track_date` 写入当天日期。
2. 首次导入传 `trackDate` 时，`track_date` 按传入值写入。
3. 重复导入传入新 `trackDate` 时，历史 `track_date` 不变。
4. 调用修改接口后，`track_date` 正确更新，`status/watched_eps/last_watch_at` 不受影响。
5. 卡片可正确展示“开始追番”“最近观看”两行时间信息。
6. 进度快捷操作后 `last_watch_at` 变化，`track_date` 保持不变。

---

## 10. 风险与处理

- 风险：用户误以为重复导入可覆盖追番时间。
  - 处理：文档与提示语明确“重复导入仅刷新番剧元数据”。
- 风险：前端日期解析受浏览器时区影响。
  - 处理：统一后端返回标准格式，前端封装格式化函数，避免隐式解析。
- 风险：继续使用 Map 入参导致字段拼写问题。
  - 处理：本任务中建议同步引入 DTO，提升类型安全与可维护性。

---

## 11. 实施顺序建议

1. 后端：导入接口增强 + 新增更新接口 + 校验逻辑。
2. 前端：API 类型与方法改造。
3. 前端：导入弹窗日期选择 + 进度弹窗日期更新。
4. 前端：卡片新增“开始追番/最近观看”展示。
5. 联调：覆盖首次导入、重复导入、修改追番时间、进度操作回归。
