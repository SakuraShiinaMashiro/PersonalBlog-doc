# 导入幂等性校验与重复提示 详细设计

## 1. 背景与范围

本设计对应 `V2.0` 开发计划中的“导入幂等性校验与重复提示”任务。

当前追番模块已支持按 `bgmId` 导入 Bangumi 条目，但重复导入时会触发数据冲突风险或缺少用户友好提示。需要将导入行为统一为“可重复执行且结果可预期”的幂等操作。

本次设计仅覆盖：

- 导入接口的幂等处理逻辑（按 `bgmId` 判重）；
- 重复导入时的数据更新策略；
- 前端“已存在”提示策略。

不在本次范围内：

- 并发竞争场景强化处理（系统仅单人使用，暂不考虑并发）；
- 新增复杂通知系统（先使用现有前端提示能力）。

---

## 2. 设计目标

1. 同一 `bgmId` 可重复导入，后端行为幂等且可预测。
2. 首次导入与重复导入都返回成功态，并区分结果语义。
3. 重复导入只刷新番剧元数据，不重置用户追番进度。
4. 前端明确提示“导入成功”或“已存在，已刷新番剧信息”。

---

## 3. 幂等语义定义

以 `blog_anime_subject.bgm_id` 为幂等键：

- 若本地不存在该 `bgm_id`：执行创建流程（`CREATED`）。
- 若本地已存在该 `bgm_id`：执行更新流程（`UPDATED`）。

两种结果都视为**成功处理**，接口返回 `code=200`。

---

## 4. 数据更新策略

### 4.1 首次导入（CREATED）

- 新增 `blog_anime_subject` 记录；
- 新增对应 `blog_anime_progress` 初始化记录：
  - `status = 0`
  - `watched_eps = []`
  - `track_date = 当前日期`

### 4.2 重复导入（UPDATED）

仅更新 `blog_anime_subject` 元数据字段：

- `title`
- `image_url`
- `eps`
- `air_date`
- `air_year`
- `air_season`

不更新 `blog_anime_progress`，尤其保持以下字段不变：

- `watched_eps`
- `status`
- `track_date`
- `last_watch_at`

说明：`track_date` 语义为“开始追番时间”，重复导入不应改写历史开始时间。

---

## 5. 接口设计

### 5.1 请求

- 路径：`POST /api/anime/import`
- 入参：

```json
{
  "bgmId": 123456
}
```

### 5.2 响应

统一 `Result<T>` 包装，`data` 返回导入结果语义：

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "action": "CREATED",
    "message": "导入成功"
  }
}
```

或：

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "action": "UPDATED",
    "message": "已存在，已刷新番剧信息"
  }
}
```

`action` 取值：

- `CREATED`：首次创建
- `UPDATED`：已存在并刷新

---

## 6. 后端改造点

### 6.1 服务层

- `AnimeService#importFromBangumi(int bgmId)` 返回导入结果对象（不再是 `void`）。
- 实现流程：
  1. 拉取 Bangumi 条目详情；
  2. 按 `bgmId` 查询本地是否已存在；
  3. 分支执行 `CREATED` 或 `UPDATED`；
  4. 返回导入语义结果。

### 6.2 控制层

- `AnimeController#importAnime` 返回 `Result<ImportResult>`（名称以代码实现为准）。

### 6.3 数据层

- 继续依赖 `blog_anime_subject.bgm_id` 唯一索引作为判重基础。

---

## 7. 前端改造点

- `animeApi.import` 增加导入结果类型定义；
- 导入后根据 `action` 做差异化提示：
  - `CREATED` -> "导入成功"
  - `UPDATED` -> "已存在，已刷新番剧信息"
- 两种情况都刷新追番列表。

---

## 8. 验收标准

### 8.1 幂等行为

- 同一 `bgmId` 连续导入多次，`blog_anime_subject` 仅保留一条记录；
- 第二次及后续导入返回 `UPDATED`。

### 8.2 数据正确性

- 重复导入后，番剧元数据可更新；
- 重复导入后，`progress.track_date` 保持不变；
- 重复导入后，`watched_eps/status/last_watch_at` 保持不变。

### 8.3 前端体验

- 首次导入看到成功提示；
- 重复导入看到“已存在”语义提示；
- 导入后列表数据刷新正确。

---

## 9. 风险与处理

- 风险：重复导入刷新元数据后，用户误以为“进度也被重置”。
  - 处理：明确约束“仅刷新 `subject`，不改 `progress`”。
- 风险：前端未区分 `CREATED/UPDATED`，提示语义不清。
  - 处理：前端按 `action` 强制分支提示。

---

## 10. 结论

本方案将导入接口定义为“成功可重复执行”的幂等操作：首次创建、重复更新，并向前端返回清晰语义结果；同时保留用户追番进度与开始追番时间，满足单用户场景下的稳定性与易用性要求。
