# PersonalBlog V2.0 需求分析文档（追番模块）

## 1. 背景与目标

### 1.1 背景
当前 V1.0 已完成追番模块的基础能力：
- 支持 Bangumi 番剧搜索与导入；
- 支持按年份 + 季度（air_year + air_season）查看番剧列表；
- 支持单集勾选与状态切换（想看/在看/已完结）。

在实际使用中，仍存在以下问题：
- 重复导入时用户反馈不明确，易产生困惑；
- 搜索失败与无结果场景区分不清；
- 列表筛选与排序维度较少，不利于回顾；
- 进度操作偏基础，缺少高频快捷动作。
- 支持按季度查看番剧列表，这个语义有错误。按照季度追番的话，应该根据番剧导入的时间进行切分，冬季的话应该是1-3月份。如果这个时间段导入的番剧的话，自动归为冬季，而不是用户自己选哪个季度的。这跟番剧的放映季度概念混淆了按追番时间查看时，
- '追番时间'应该取哪个时间点？
导入时间，但是否应该支持自己选择什么时候开始追番的，而不是直接根据导入时间一一刀切
- 现有的 air_year/air_season 字段是否保留用于筛选'放映季度'？
这个用于筛选番剧的放映时间吧，而不是自己的追番时间。比如`/api/anime/search`不是返回了date吗，也就是首播时间，还有这两个字段语义有问题，应该填写的是番剧的首播年份，和这部番剧播出时候所在的季度
- 状态切换有问题，不应该让用户手动选择想看，在看，已完结，应该根据已经看了的集数，自动跳转状态。此外，状态应该改为想看、在看、已看完比较合理
### 1.2 目标
V2.0 聚焦追番模块深化，目标为：
- 将“可用”提升为“稳定、清晰、可持续使用”；
- 完成按追番时间 年份 + 季度 筛选查看能力，或者单纯能够查看这一整年看的番剧
- 优化搜索、导入、筛选、进度管理的整体体验。
- 状态切换问题修复

## 2. 范围定义

### 2.1 In Scope（本期范围）
- **搜索与导入闭环优化**：实现幂等导入提示、搜索异常与无结果的准确区分；
- **追番时间维度聚合**：支撑追番日期（`track_date`）记录，增强按追番年份/季度进行列表聚合查看的能力；
- **多维筛选与排序增强**：在放映季度基础上，增加追番时间、追更热度等要素的交叉筛选与灵活排序；
- **高频进度快捷操作**：引入“看到第 N 集”、“一键看完”等快捷动作，完善状态与进度的自动联动逻辑；
- **全局错误处理机制**：针对外部 API 建立健壮的异常捕获与反馈体系，提升系统在弱网或接口异常下的可用性。

### 2.2 Out of Scope（本期不做）
- 每日打卡模块；
- 全局统计看板；
- 全站搜索与标签体系重构；
- 多用户权限系统全面改造。

## 3. 用户场景与核心流程

### 3.1 核心用户场景
- 场景 A：用户搜索新番并导入到个人追番库。
- 场景 B：用户每天更新看到的集数并快速同步状态。
- 场景 C：用户按追番时间/放映季度/状态/最近追更回顾自己的追番记录。

### 3.2 核心流程
1. 用户输入关键词进行搜索；
2. 在结果列表中选择目标番剧并导入；
3. 导入时系统自动记录追番时间（默认当前日期，用户可修改）；
4. 导入后进入按追番时间归类的列表，更新集数进度；
5. 系统自动记录最近追更时间；
6. 用户通过筛选与排序快速回顾追番状态。

## 4. 功能需求

### 4.1 搜索与导入
- 支持关键词搜索 Bangumi 番剧；
- 搜索接口需区分“无数据”与“请求失败”，搜索不到数据前端界面应该给出合理的提示
- 导入需具备幂等行为：重复导入给出明确提示；
- 导入成功后可立即在本地列表中可见。
- 默认使用导入时间作为追番时间，精确到年月日，用户也可以手动修改追番时间。

### 4.2 列表与筛选
- 支持按追番时间（年+季度）筛选：根据用户开始追番的时间归类；
- 支持按照追番时间的年度进行筛选，用户能够直接查看某一年看过的所有番剧
- 支持查看全部状态下的番剧的功能
- 支持按放映季度（air_year + air_season）筛选：根据番剧首播时间归类；
- 支持按“追番时间”与“首播时间”进行灵活排序；
- 默认展示逻辑清晰，筛选条件可持续保留（同页操作期间）。

### 4.3 进度管理
- 支持单集已看/未看切换；
- 支持快捷操作：看到第 N 集、一键看完、重置进度；
- 集数操作应进行有效性校验（范围合法）；
- 已看集数在展示与存储层保持有序、去重。

### 4.4 状态管理
- 将状态想看/在看/已完结 修改为 想看/在看/已看完
- 支持按状态筛选（想看/在看/已看完）；
- **自动状态联动逻辑**（用户不可手动修改状态）：
  1. 未看过任何一集：状态为“想看”；
  2. 已看 1 集以上且未全部看完：状态为“在看”；
  3. 已看完所有集数：状态为“已看完”。

## 5. 非功能需求

### 5.1 性能
- 常规列表查询响应时间目标：< 500ms（本地开发环境除外）；
- 搜索接口超时可配置，避免长时间阻塞。

### 5.2 稳定性
- 外部 API 异常时系统应返回可识别错误，不影响本地已导入数据浏览；
- 导入与进度更新需保证数据一致性。

### 5.3 可用性
- 前端对关键操作提供明确反馈（成功/失败/重复导入）；
- 错误提示面向用户可理解，避免仅输出技术异常。

### 5.4 可维护性
- 后端优先使用明确 VO/DTO，而非松散 Map 结构；
- 保持接口语义一致，便于后续扩展。

---

## 6. 验收标准与里程碑

### 6.1 验收标准（简版）
- 重复导入同一番剧时，系统给出明确提示且不产生重复记录；
- 用户可准确按“追番年度”、“追番季度”或“已看完”进行聚合查询；
- 进度更新会自动触发状态切换（想看 -> 在看 -> 已看完），前端去除手动修改功能；
- 用户可通过“看到第 N 集”或“一键看完”在 2 次点击内完成进度批量更新；
- 列表支持按“追番时间”与“首播时间”进行多重排序；
- 搜索失败时，前端能够区分展示“连接异常”与“未找到结果”的友好提示。

### 6.2 里程碑建议
- 里程碑 1：数据结构与接口契约调整（幂等、日期字段、状态自动计算逻辑）；
- 里程碑 2：后端核心功能实现与单元测试；
- 里程碑 3：前端交互优化与回归验证。

### 6.3 风险与依赖
- 依赖 Bangumi API 可用性与网络质量；
- 导入高频场景下可能出现第三方限流；
- 需要预留失败重试与降级提示策略。
