# PersonalBlog V2.0 需求分析文档（追番模块）

## 1. 背景与目标

### 1.1 背景
当前 V1.0 已具备基础追番能力：
- 支持 Bangumi 番剧搜索与导入；
- 支持按放映季度（`air_year` + `air_season`）查看番剧列表；
- 支持单集勾选与状态切换。

在实际使用中存在以下问题：
- 重复导入反馈不明确，用户难以判断是否已入库；
- 搜索失败与无结果场景区分不清；
- 缺少按“我何时开始追”的时间维度回顾能力；
- 进度操作偏基础，缺少高频快捷动作；
- 状态与进度存在手动维护成本，容易不一致。

### 1.2 V2.0 目标
- 将追番模块从“可用”提升到“稳定、清晰、可持续使用”；
- 新增按追番时间（年/季度）回顾能力，同时保留按放映季度筛选；
- 优化搜索、导入、筛选、进度管理的一体化体验；
- 建立“进度驱动状态”的自动联动规则。

---

## 2. 术语与字段定义（必须统一）

### 2.1 术语定义
- **追番时间（trackDate）**：用户开始追这部番剧的日期，用于“个人追番时间维度”统计与筛选；
- **放映时间（airDate）**：番剧首播时间，由外部数据源提供；
- **放映季度（airYear + airSeason）**：基于放映时间推导出的季度，表示番剧播出时点，不表示用户追番时点；
- **追更时间（lastWatchAt）**：用户最后一次更新该番剧观看进度的时间。

### 2.2 字段规则
- `trackDate`：
  - 类型：`date`（精确到日，不含时分秒）；
  - 默认值：导入当日；
  - 可修改：是（仅允许改到 `today` 及之前）；
  - 为空策略：不允许为空。
- `airYear` / `airSeason`：
  - 来源：由 `airDate` 计算或外部数据直接提供；
  - 用途：仅用于放映维度筛选；
  - 不允许与 `trackDate` 混用。
- 季度定义统一：
  - Q1：1-3 月，Q2：4-6 月，Q3：7-9 月，Q4：10-12 月。

---

## 3. 范围定义

### 3.1 In Scope（本期范围）
- 搜索与导入闭环优化：幂等导入、重复导入可识别提示；
- 追番时间维度聚合：支持按 `trackDate` 的年、季度筛选；
- 多维筛选排序：支持状态、追番时间、放映季度组合筛选；
- 高频进度操作：支持“看到第 N 集”“一键看完”“重置进度”；
- 状态自动计算：状态不再由用户手动修改；
- 外部 API 错误处理：区分“无结果”与“外部请求失败”。

### 3.2 Out of Scope（本期不做）
- 每日打卡模块；
- 全局统计看板；
- 全站搜索与标签体系重构；
- 多用户权限系统改造。

---

## 4. 核心流程

1. 用户输入关键词搜索番剧；
2. 用户在结果中选择番剧并导入；
3. 导入时默认写入 `trackDate = today`，用户可改为历史日期；
4. 系统写入或更新本地番剧记录（幂等）；
5. 用户更新观看进度（单集或批量）；
6. 系统更新 `lastWatchAt` 并自动计算状态；
7. 用户按追番时间/放映季度/状态进行筛选和回顾。

---

## 5. 功能需求

### 5.1 搜索与导入
- 支持关键词搜索 Bangumi 番剧；
- 搜索结果分三类：
  - 成功且有数据；
  - 成功但无数据；
  - 请求失败（网络、超时、三方异常）。
- 导入具备幂等行为：同一番剧重复导入不新增重复记录；
- 幂等判定主键：`bangumiId`（唯一）；
- 导入成功后列表即时可见。

### 5.2 列表、筛选与排序
- 支持按追番时间筛选：
  - 年度筛选（例：2026）；
  - 季度筛选（例：2026-Q1）。
- 支持按放映季度筛选（`airYear` + `airSeason`）；
- 支持按状态筛选（全部/想看/在看/已看完）；
- 支持排序字段：
  - `trackDate`（开始追番时间）；
  - `airDate`（首播时间）；
  - `lastWatchAt`（最近追更时间）。
- 默认排序：`lastWatchAt desc`，空值排最后；
- 同页操作期间保持筛选条件。

### 5.3 进度管理
- 支持单集已看/未看切换；
- 支持快捷操作：
  - 看到第 N 集；
  - 一键看完；
  - 重置进度（清空已看集）。
- 进度操作校验：
  - `N >= 0`；
  - 若总集数 `totalEpisodes` 已知，则 `N <= totalEpisodes`；
  - 已看集集合去重并保持升序。
- 任意进度写操作成功后，更新 `lastWatchAt`。

### 5.4 状态管理（自动联动）
- 状态枚举统一为：`WANT_TO_WATCH`（想看）、`WATCHING`（在看）、`WATCHED`（已看完）；
- 用户不可手动设置状态；
- 状态由进度自动计算：
  1. 已看集数 = 0 -> 想看；
  2. 已看集数 > 0 且未看完 -> 在看；
  3. 已看完全部集数 -> 已看完。

### 5.5 状态计算边界规则
- 若 `totalEpisodes` 未知（空或 0）：
  - 已看集数 = 0 -> 想看；
  - 已看集数 > 0 -> 在看（不可判定已看完）。
- 执行“重置进度”后状态必为“想看”。

---

## 6. 接口契约要求（V2.0 最小集）

### 6.1 统一响应
- 沿用 `Result<T>`：`code`、`message`、`data`。

### 6.2 错误语义（必须可区分）
- 搜索无结果：`code = 200`，`data = []`，`message = "ok"`；
- 外部 API 失败：`code != 200`，`message` 给出可读错误（如 `bangumi api timeout`）；
- 参数错误：`code != 200`，`message` 明确指出非法字段。

### 6.3 导入幂等行为
- 首次导入：返回成功并标记 `imported = true`；
- 重复导入：返回成功并标记 `imported = false`，`message = "already imported"`；
- 数据库层必须有唯一约束（`bangumi_id unique`）保证并发下幂等。

---

## 7. 非功能需求

### 7.1 性能
- 列表查询目标：在 1 万条个人追番数据规模下，P95 < 500ms（不含前端渲染）；
- 外部搜索超时可配置，默认 5s。

### 7.2 稳定性
- 外部 API 异常不影响本地已导入列表浏览；
- 导入和进度更新需保证事务一致性；
- 并发重复导入不产生脏数据。

### 7.3 可用性
- 关键操作有明确反馈：成功、失败、重复导入；
- 用户提示应避免暴露技术栈细节。

### 7.4 可维护性
- 后端优先使用 DTO/VO，避免松散 Map；
- 规则集中在 Service 层，Controller 保持薄逻辑。

---

## 8. 数据迁移与兼容

- 历史数据新增 `track_date` 时，回填策略：
  - 优先使用历史导入时间；
  - 无导入时间则使用记录创建日期；
  - 都无则回填脚本执行日期。
- 旧状态值 `已完结` 迁移为 `已看完`；
- 前端状态展示文案统一为：想看 / 在看 / 已看完。

---

## 9. 验收标准

- 重复导入同一 `bangumiId` 不产生重复记录，前端得到“已存在”可读提示；
- 用户可按 `trackDate` 的年份和季度筛选，并可与状态、放映季度组合筛选；
- 进度变更可自动触发状态切换，且前端不再提供手动改状态入口；
- “看到第 N 集”“一键看完”“重置进度”可正确更新已看集、状态、`lastWatchAt`；
- 搜索场景中，“无结果”和“请求失败”在接口和前端提示层均可区分；
- 历史数据迁移后，列表可正常展示且状态文案一致。

---

## 10. 里程碑建议

- 里程碑 1：数据结构调整与迁移脚本（`track_date`、状态枚举、唯一约束）；
- 里程碑 2：后端接口与核心规则实现（幂等、状态机、错误语义）；
- 里程碑 3：前端交互与筛选排序改造；
- 里程碑 4：联调、回归、验收。

## 11. 风险与依赖

- 依赖 Bangumi API 可用性和限流策略；
- 外部超时与失败重试策略需与前端提示协同；
- 历史数据质量可能影响 `track_date` 回填准确性。
